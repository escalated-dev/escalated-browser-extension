# Browser extension research: helpdesk (Escalated) and inventory (Inventoros)

Date: 2026-11-25. Web research only. Store counts and ratings come from search snippets and may be stale; verify on the live listings before quoting them. Where I could not confirm something, it says so.

## 1. Prior art

### Helpdesk

Key finding: the big vendors mostly do NOT ship a Chrome extension as the main agent tool. The agent works in the web app. Extensions around helpdesks are mostly third-party utilities, plus CRM-style Gmail sidebars.

Take-aways from reviews:
- Praise goes to small, single-job tools that save clicks every day: tab management, auto-refresh, unread badge, notifications, templates.
- Complaints: breaks when the host UI changes (DOM-scraping extensions rot, e.g. Zendesk Auto Refresh "does not work anymore", Freshdesk gadget), settings that reset, slowing Gmail (HubSpot), overly broad permissions, single-inbox limits.
- Gmail add-ons (Workspace Marketplace) are the vendor-preferred route for Gmail; extensions that inject into Gmail's DOM are the fragile route.

Take-aways: the proven inventory pattern is "capture from the page I am on" (import product, clip supplier price/SKU into a product or PO) and "overlay on the page" (Keepa). Both depend on per-site parsing, which breaks; keep supported sites few, or use generic JSON-LD / schema.org Product markup, Open Graph, and the visible selection instead of site-specific scrapers.

## 2. What is worth building (my read, based on the above)

Escalated (helpdesk), ordered by value for effort:
1. Agent toolbar + side panel: ticket queue with unread/assigned counts as a badge, desktop notifications for new tickets and replies (alarms polling the token API), open ticket, quick reply, canned reply, KB search/insert. Matches the praised single-job tools (Quicktab, Notify-Me, Unread Counter, Macha).
2. "Create ticket from this page": right-click or selection, prefill subject, URL, selected text, optional screenshot. Works on any page with no content script on every site (use activeTab).
3. Gmail/Outlook sidebar (create ticket from email, show customer's tickets): high value but highest cost and fragility. Prefer Gmail add-on / Outlook add-in or the side panel with a user-triggered "read this email" over injecting into Gmail's DOM. Defer.

Inventoros (inventory):
1. Side panel lookup: search by SKU/barcode/name, show stock per location, price, open POs; works anywhere (on a supplier page, paste or select the SKU, context menu "look up selection").
2. "Clip to product / PO": from a supplier or marketplace page, read JSON-LD Product data (name, SKU/GTIN, price, image, URL) and prefill a new product or a PO line. Generic, no per-site scrapers.
3. Alerts: low stock and new order notifications via alarms polling.
4. Barcode: webcam scanning in an extension is possible but a phone app or the web app is a better fit; low priority.

## 3. Manifest V3 constraints

- Side panel: `sidePanel` permission, `side_panel.default_path` or `setOptions` per tab, Chrome 114+, `open()` Chrome 116+ and only from a user gesture (action click, shortcut, context menu, click in extension page or content script). `setPanelBehavior({openPanelOnActionClick:true})` opens it from the toolbar icon. https://developer.chrome.com/docs/extensions/reference/api/sidePanel
- Service worker lifetime: stops after 30 s idle; a single event or request over 5 min is killed; a fetch response slower than 30 s also ends it; events and extension API calls reset the timer; WebSockets keep it alive since Chrome 116. Do not hold state in globals. https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle
- Polling: use `chrome.alarms`, not setInterval. Minimum period 30 s from Chrome 120 (the alarms reference page says at most once per second; the lifecycle page says 30 s; use 60 s or more in practice). Alarms do not wake a sleeping device and fire once on wake. Persistence varies across browsers, so recreate alarms on every service-worker start and set `persistAcrossSessions` explicitly. Notifications need the `notifications` permission. https://developer.chrome.com/docs/extensions/reference/api/alarms , https://developer.chrome.com/docs/extensions/reference/api/notifications . A server push (SSE or WebSocket from the self-hosted app) is nicer than polling but a WebSocket only helps while the worker runs; polling by alarm is the dependable baseline.
- Self-hosted base URL: you cannot list the user's host in the manifest. Declare `optional_host_permissions` (e.g. `https://*/*` and `http://*/*` for LAN installs) and call `chrome.permissions.request({origins:[origin]})` from a button click after the user types the URL. Paths are ignored; grant is per origin. http and https are separate patterns. Chrome prompts only if the grant adds new warnings. https://developer.chrome.com/docs/extensions/reference/api/permissions . A broad optional pattern is still declared in the manifest, which the store may look at; justify it in the listing.
- CORS: extension pages and the service worker with matching host permission can call the API without server CORS changes. Content scripts are subject to the page's CORS, so route all API calls through the service worker via messaging, accept only specific inputs (ids), never arbitrary URLs. https://developer.chrome.com/docs/extensions/develop/concepts/network-requests . If the user instead has not granted the host, the server needs CORS headers; avoid that dependency.
- Token storage: `chrome.storage.session` is memory only (10 MB), not exposed to content scripts by default, cleared on browser restart. `chrome.storage.local` is on disk (10 MB), exposed to content scripts by default (use `setAccessLevel('TRUSTED_CONTEXTS')`); the docs do not state it is encrypted. Practical pattern: keep the token in `storage.local` with trusted-contexts access (so users are not asked to log in after each restart), or session-only as an opt-in "more secure" mode; never put it in content scripts or page context; use a scoped, revocable Sanctum token with minimal abilities. Do not use `storage.sync` for tokens (syncs to Google). https://developer.chrome.com/docs/extensions/reference/api/storage . Better still: an OAuth-like "connect" flow where the app issues a token to the extension (e.g. a page in the app that posts the token via `externally_connectable` or a copy/paste code).
- Gmail/Outlook web content scripts: possible with match patterns for `https://mail.google.com/*` and `https://outlook.office.com/*`, but you parse and inject into a DOM you do not own. InboxSDK is the common Gmail helper; its docs and examples are MV2-era and it loads remote script, which MV3 forbids; no confirmed MV3-clean release found. gmail.js claims MV2 and MV3 compatibility. https://www.github.com/InboxSDK/InboxSDK , https://github.com/vknow/gmail.js . HubSpot's reviews show the cost: Gmail slowdowns and permission complaints. For Outlook, Microsoft's own route is an Office add-in, which HubSpot also uses. https://knowledge.hubspot.com/connected-email/get-started-with-the-hubspot-sales-chrome-extension
- Unauthenticated use of a second "version" (read-only mode) should still go through the same permission flow.

## 4. Chrome Web Store policy

- Single purpose: must be "narrow and easy to understand", described in the dashboard single-purpose field. Allowed: a narrow focus area or browser function. Permissions must match the purpose; request the narrowest permission; no permissions for unbuilt features. https://developer.chrome.com/docs/webstore/program-policies/policies , https://developer.chrome.com/docs/webstore/program-policies/quality-guidelines-faq
- One extension for both products: risky. Policy says separate distinct features into different extensions users can install independently; bundling unrelated functionality is a violation. A helpdesk client and an inventory client are different subject areas, even if one company makes both. A defensible framing is not obvious. Recommendation: two listings (or one shared codebase built twice with different manifests, names, and permissions). Policy also forbids duplicate extensions offering the same experience, so make them clearly different.
- Privacy policy: required if you handle user data (collecting, transmitting, using, sharing), even if stored locally. Ticket and stock data fetched from the user's own server and tokens count; post a short policy, complete the dashboard Privacy practices tab, give prominent in-product disclosure and consent, use HTTPS. A "user-specified server" client may be generally exempt from Limited Use and secure-transmission rules for data sent to that server (the FAQ names FTP and IRC as examples; whether a helpdesk API counts is not stated, so plan to comply anyway). Say plainly that the developer receives no data. https://developer.chrome.com/docs/webstore/program-policies/user-data-faq
- Remote code ban: all logic must ship in the package. No remote scripts, no eval of remote strings, no remote-driven interpreters. Fetching data and remote config is fine. Do not load a UI bundle from the user's self-hosted server (tempting: embed the Escalated Vue app in an iframe or load its JS). Embedding the server's pages in an iframe is not code loading by the extension, but is a gray area for review; keep the side panel a bundled UI that calls the JSON API. https://developer.chrome.com/docs/extensions/develop/migrate/improve-security . Minification is allowed; obfuscation is not.
- Review time: most within a few days, up to a few weeks; longer for new developers, new extensions, broad host permissions (`https://*/*`, `<all_urls>`), and big code changes; contact support if pending over 3 weeks. Optional broad host permissions are likely to draw the same scrutiny. https://developer.chrome.com/docs/webstore/review-process
- Content-script toolbars injected into every page are discouraged; prefer an action popup or side panel.

## 5. Cross-browser

- Edge: Chromium; Chrome extensions are code-compatible with minimal changes. Remove `update_url`, do not use "Chrome" in name or description, publish separately to the Edge Add-ons site (separate developer account). Side panel is available on Edge's Chromium base, but Edge's own supported-API list should be checked for `sidePanel` before relying on it (I did not confirm it). https://learn.microsoft.com/en-us/microsoft-edge/extensions/developer-guide/port-chrome-extension . Extra work: small (a day or less plus store submission).
- Firefox: moderate. Differences:
  - Background: Firefox MV3 uses non-persistent event pages (`background.scripts`), not service workers; Chrome uses `service_worker`. A manifest can declare both keys for one build in modern versions, but MDN advises keeping a manifest per browser and swapping at build time. Keep listeners at top level, state in storage, alarms not timers (good practice for both).
  - Namespace: `browser.*` with promises in Firefox; `chrome.*` in Chrome; use `globalThis.browser ?? globalThis.chrome` or webextension-polyfill. https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Build_a_cross_browser_extension
  - Side panel: Firefox has no `sidePanel`; use `sidebar_action` + `browser.sidebarAction` (always per-window, opens on first install, document persists across tabs). Feature-detect and share the same panel HTML. https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/user_interface/Sidebars
  - Host permissions: since Firefox 127 install prompt shows `host_permissions`; users can revoke any host permission, so always check and re-request. `optional_host_permissions` plus `permissions.request` works the same. https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/
  - Remote code is also blocked by stricter CSP; AMO review needs readable source or build instructions for minified bundles (I could not load the AMO policy page to confirm timing).
  - Firefox needs an add-on id (`browser_specific_settings.gecko.id`) and a separate AMO listing.
  - Estimated extra work: 2 to 4 days for build split, sidebar, background differences, and testing; more if Gmail content scripts are included.
